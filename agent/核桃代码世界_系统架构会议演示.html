今天不从复杂名词开始。我们只回答一个问题：学生写下一段代码以后，它怎样变成世界变化、教学反馈和学习记录。

01 · 核心价值

不是“提交代码后打分”，而是让代码真实改变世界

学生接到任务
→
编写 C++ Skill
→
小核桃真实调用
→
世界发生变化
→
AI 基于结果教学
→
沉淀学习证据

学生入口

Godot 学生端

写代码、编译运行、观察世界、接收反馈。

教师入口

飞书智能助手

权限化查询学生和班级情况，生成报告草稿。

贯穿原则

事实先于表达

AI 只能根据已经产生的真实结果进行教学。

这里强调产品区别：学生代码不是一份静态作业，而是一个可以被小核桃调用的 Skill。教学反馈也不是泛泛聊天，而是基于这次真实运行。

02 · 总体架构

把系统看成一条五段式的编程学习流水线

01 / 统一语言

机器合同边界

统一请求格式、返回格式和错误规则。

02 / 接单调度

后端应用层

接收、排队、查询，并把任务交给正确模块。

03 / 教学导演

智能体编排

决定谁回答、看什么事实、这一轮怎么教。

04 / 客观裁判

客观执行链

运行学生代码，判断世界实际发生了什么。

05 / 档案总账

状态与异步投影

保存原始事实，并整理成当前学习画像。

程序负责客观事实、教学门禁和状态提交；Agent 负责受约束的解释、提问和总结。
这五层可以用五个大白话角色记住：合同像统一表格，应用层像业务前台，Agent 像教学导演，执行链像实验室加裁判，状态层像档案室。

03 · 机器合同边界

先约定大家怎么说话，再分别开发

PRODUCT REST

产品体验接口

任务、工作区、代码草稿、Agent 交互和代码修改确认。

实现：从数据库组装页面需要的数据。

GAME REST

游戏命令与查询

编译、激活、Agent Turn、Command、Run、世界和 Evidence。

实现：写操作先建任务，查询操作读取结果。

WORLD WSS

世界实时通道

只推送已经提交的移动、浇水、资源变化等世界事件。

实现：按序推送，断线后从上次序号补发。

FEISHU REST

飞书集成接口

学生与班级查询、脱敏证据、内容候选、审批和报告草稿。

实现：先验权限，再脱敏查询并记录审计。

合同画好 = 施工图完成
不等于对应功能已经全部建好

202 Accepted 的含义

只表示后端已经可靠接单。前端还要拿着 command_id 和查询地址继续看最终结果。

四类接口分工必须讲清。尤其是 202 不是成功；WSS 只播已提交世界事件，Command、Run 和恢复仍以 HTTP 查询为准。

04 · 后端应用层

负责把事情接住、排好、交出去

页面整理员

产品应用服务

组合任务、会话、代码和交互记录，提供页面视图；负责草稿与 Patch 决定等产品能力。

游戏入口

命令受理 / 查询处理器

接收编译和运行请求；查询 Command、Run、世界状态和 Evidence。

可靠任务表

命令存储 + 执行作业

把请求和稳定编号写入数据库；同一请求重复提交，不新建第二个任务。

后台工作人员

持久化命令 Worker

领取待处理任务，调用 Agent、Sandbox 和 WorldEngine，记录最终状态。

教师服务

飞书应用服务

统一处理教师权限、数据脱敏、审计、内容候选与报告草稿。

实时广播员

世界事件发布器

从“待发送箱”读取已提交世界事件，发送给在线 Godot 客户端。

应用层负责调度，但它自己不运行 C++，也不临场决定应该怎么教。
命令存储和 Worker 是这里的主链：入口先把任务可靠写下，再由后台处理。飞书服务和实时发布器属于两条对外支线。

05 · 智能体编排

先决定谁来说，再决定这一轮怎么教

Agent Hub一轮教学的总导演
→
Role Router选择角色或不响应
→
Context Builder准备可信材料
→
教学策略决定阶段与上限
→
Shared Runtime让角色完成本轮回答
→
校验并提交合格后才正式保存

Agent Hub

防止同一事件重复处理，串起选角色、准备材料、执行和保存。

角色路由器

任务开始找芽芽；运行找小核桃；失败找教学或 Bug；完成找书书。

上下文构建器

精确读取当前任务、代码、Run、世界、Evidence、画像和最近对话。

角色路由器只回答“谁说话”，不回答“教到什么程度”。上下文也不是把数据库全塞给模型，而是只拿本轮精确绑定的事实。

06 · PedagogyPolicy

确定性规则：相同事实，得到相同教学决定

回顾 REVIEW

没有画像、先修证据不足、复习到期，或之前得到的帮助过多。

启发 HEURISTIC

学生具备基础，正在早期探索，但还没有明确失败证据。

纠错 RECTIFICATION

编译、测试、运行或世界证据已经证明具体偏差。

总结 SUMMARIZATION

任务完成事件和当前有效成功证据同时存在。

任务客观完成 → 总结　｜　有失败证据 → 纠错　｜　需要唤起旧知识 → 回顾　｜　其他探索 → 启发

知识点怎么选？

根据任务配置和本轮 Evidence 对应：少浇一块 → 循环边界；一直不结束 → 终止条件；移动越界 → 边界判断。

为什么不交给模型？

阶段、权限和提示上限需要稳定、可测试、可回放；模型只负责在边界内组织语言。

“确定性”不是死写很多任务 ID，而是底线规则写在代码里，知识点、阈值和先修关系放在带版本的教学配置里。角色和阶段仍是两条独立轴。

07 · 提示阶梯

先少说一点，再根据连续失败逐步增加帮助

等级 0失败 0～1 次只描述现象并提问
等级 1连续失败 2 次指出应检查的代码区域
等级 2连续失败 3～4 次解释相关概念或边界条件
等级 3连续失败 5 次以上给局部修改方向或伪代码

学生明确请求提示时，原始等级加 1；再受任务和当前教学阶段的上限约束。

后续能力：等级 4 / Skill Patch

不是到等级就自动改代码

  • 必须处于纠错阶段，且角色有教学权限
  • 任务规则允许，并有直接相关的失败 Evidence
  • 代码基线固定，学生主动请求或达到有效阈值
  • 只提出结构化修改，最终仍需学生确认

当前运行时仍强制关闭 Patch 与完整答案资格。

提示等级是“最多可以透露多少”，不是要求模型一定把信息全部说满。
这里要说“同一 failure_key 的连续失败”，不是所有失败总数。当前阶段最高只开放到等级 3；等级 4 和 Patch 是目标设计，不要说成现有功能。

08 · TeachingDirective × TurnContext

上下文是学生材料包，教学指令是里面的本轮任务单

读取可信事实任务、代码、Run、Evidence、画像
→
教学策略判断阶段、知识点、提示上限
→
生成教学指令本轮不可变约束
→
固化为本轮上下文事实 + 指令一起交给 Runtime

CONTEXT · 发生了什么

八块土地只浇了七块

代码包含 i < length - 1；连续失败 2 次；最后一块仍是干的；Evidence 为本次 Run。

→

DIRECTIVE · 这一轮怎么教

纠错 · 循环边界 · 等级 1

只允许问题和低等级提示；不允许 Patch；必须引用本次运行 Evidence。

✓ 可以说

“最后一块没有被浇到，可以检查循环条件决定了它在哪里停止。”

× 不能直接说

“把 length - 1 改成 length。”

上下文回答“发生了什么”，教学指令回答“面对这些事实怎么教”。顺序是先取事实，再算指令，最后把二者固化成同一个 TurnContext。

09 · Shared Agent Runtime

一套统一执行器，加载不同“角色卡”完成不同任务

接收角色和资料包

角色已经选好，阶段也已经确定。

加载角色配置

人设、语气、可用工具、回答长度和格式。

整理给模型的材料

真实事实、教学指令和固定返回格式。

调用模型

模型负责理解、解释和组织语言。

必要时调用工具

先检查权限和参数，再执行真实工具。

把结果交回模型

没有真实工具回执，不能声称世界已改变。

获得固定格式回答

回复、问题、Evidence 引用和候选推断。

进行质检

检查角色、阶段、提示上限、证据和 Patch 权限。

返回正式结果

合格后交给 Agent Hub 统一保存。

一轮只运行一个角色；输出不合格只修正一次，仍失败就用基于真实 Evidence 的固定兜底回复。
Runtime 不选角色、不定教学阶段、不判断任务成功，也不直接改世界、代码或画像。它只是按已经给定的角色卡和任务单执行这一轮。

10 · 运行时配套模块

模型回答还不是正式结果，必须先过质检

ROLE CONFIG

角色配置

长期角色卡：身份、语气、工具权限、输出限制。

LLM ADAPTER

大模型适配器

把统一请求翻译给具体供应商，便于未来替换模型。

VALIDATOR

回答质检员

检查格式、角色、教学指令、Evidence 和代码修改权限。

TURN COMMIT

轮次提交接口

把消息、交互、推断候选和后续事件一次性保存。

模型可以做

  • 解释、提问和角色化表达
  • 引用 Evidence 提出学习推断候选
  • 在未来门禁允许时提出 Patch 候选

模型不能做

  • 决定任务是否成功
  • 提高提示等级或改变教学阶段
  • 直接修改世界、代码或学生画像
校验失败不会回滚已经完成的代码运行和世界结果。模型不可用时，学生仍能看到编译、运行、世界轨迹和基础模板反馈。

11 · 客观执行链

学生代码想做什么，与世界实际发生什么，分开判断

工具注册表绑定学生、Skill 版本和参数
→
C++ Sandbox编译、测试、隔离运行
→
动作意图移动、浇水、扫描……
→
WorldEngine按固定规则判断结果
→
世界工作单元一次性提交全部事实
→
正式事实包Run + Event + Evidence + 回执

工具注册表 / Skill 调用

规定角色能用哪些工具，并固定准确的学生、代码版本、输入和世界版本。

固定镜像 C++ Sandbox

限制运行时间、资源、动作数量和输出；死循环只终止本次运行。

确定性 WorldEngine

判断越界、障碍、资源、动作结果和任务是否完成；相同输入得到相同结果。

世界工作单元

检查世界版本，一次性保存新状态、事件、Run、Evidence、回执和待发送记录。

FACT：已经正式确认的事实包

返回给 Runtime 做教学、供 Godot 播动画、供教师查询，也触发学习画像更新。只有世界提交回执才能证明世界真正改变。

Sandbox 只说“代码想做什么”；WorldEngine 才决定“世界实际上发生了什么”。
不要把 ActionIntent 直接当动画或世界事实。Sandbox 成功只代表得到了合法动作列表，只有世界原子提交成功才算真正改变世界。

12 · 版本化状态

数据库不仅存“最后结果”，还保存完整过程和版本

TASK / CONTENT

任务与内容版本

学生开始后绑定固定任务版本，后续编辑不会突然改变正在进行的会话。

TEACHING SPEC

内部教学规范

知识点、先修关系、提示规则和 Patch 权限的版本化配置。

AGENT INTERACTION

产品智能体交互

保存角色回复、教学问题、成长总结和未来的 Patch 决定。

POSTGRESQL

系统总账本

保存任务、代码、命令、运行、世界、Evidence、交互、画像与审计。

事件存储 / 投影发件箱

保存事实时，同时写下“后续还要处理”的待办。即使服务重启，事件也不会永久丢失。

为什么要带版本？

写入前先确认当前版本没有被别人改变，避免旧结果把新状态静默覆盖。

原始事实保留下来，页面视图和学习画像都可以重新整理、重新计算。
TeachingSpec 目前仍是需要继续完善的可配置能力。Product AgentInteraction 的 list/get 已经正式交付，但其余 Product 能力不能一起算作完成。

13 · 异步投影

原始 Evidence 像银行流水，学习画像像当前余额

客观 Evidence编译、测试、运行、世界结果
＋
Agent 推断候选必须引用 Evidence 和置信度
→
学习证据发件箱不可变、可重试、按序号排列
→
投影 Worker去重、连续消费、应用规则
→
学习画像快照阶段、帮助程度、复习时间、版本

学习证据发件箱

把客观事实和模型候选分开记录；模型推断不能直接变成画像。

学习画像投影 Worker

按每个学生的连续序号处理；重复证据不重复计算，缺一条不能直接跳过。

投影接口与画像快照

统一更新入口；每次有效更新版本精确加一，新画像参与下一轮教学。

Agent 可以说“这个学生可能理解了循环边界”；是否写进画像，仍由程序根据 Evidence 判断。
这一条链当前已经有持久化 Worker、版本校验、重建和下一轮画像读取。投影失败只影响画像新鲜度，不回滚已提交的 Run、World 或 Agent 回复。

14 · 四道保险

每一步分别提交事实，失败后靠回执对账

A

命令耐久受理

保存 Command、Job、原请求和幂等编号。服务重启任务不丢，重复请求不新建。

202 只是接单
B

客观事实提交

一次保存世界、Event、Run、Evidence、调用回执和发件箱。

世界事实全或无
C

Agent 轮次提交

一次保存回复、交互、Evidence 关联、推断候选和后续事件。

防重复与旧结果覆盖
D

学习画像投影

按连续序号和当前版本更新，版本精确加一，重复证据不重复晋级。

可重建、可追溯
不把 Sandbox、模型调用和四个提交阶段包成一个超长操作；每阶段留下可查询的正式回执。
用“保险”比“事务”更好讲。A 防丢单和重复；B 防世界只改一半；C 防回复与记录不一致；D 防画像重复计算和版本混乱。

15 · 从点击运行到下一轮教学

17 · TAKEAWAYS

最后记住三句话

01 · 接单

202 只代表后端已经接单

不代表代码运行成功，客户端还要继续查询最终结果。

02 · 事实

Sandbox 产生动作意图

WorldEngine 才决定真实世界结果，只有提交回执能证明世界改变。

03 · 教学

Agent 负责受约束的表达

最终阶段、权限、代码、世界和画像都由程序校验并提交。

先保证代码真实改变世界、世界结果可以验证、AI 教学有事实依据，再按真实需求逐步扩展。
收尾后停顿，邀请提问。如果时间紧，整场只讲第 2、3、4、6、8、9、11、13、16、17 页也能形成完整主线。
